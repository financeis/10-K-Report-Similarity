**전체 방향은 타당합니다. 다만 ‘관계를 찾아 보여주는 시제품’으로는 착수할 수 있지만, ‘근거를 신뢰할 수 있는 관계도’가 되려면 판정·평가·저장 설계를 먼저 보완해야 합니다.**

[계획 문서](/C:/Users/imyon/Documents/10-k-report/10-K-Report-Similarity/docs/relation-map-plan.md)와 기존 수집·정제·유사도·수익률 코드를 대조했습니다. Jev 공식 문서도 확인했습니다. 문서와 코드는 수정하지 않았으며, 저장소 밖에서 실행했다는 사전 조사의 수치는 재현하지 않았습니다.

유지할 만한 핵심 설계는 다음과 같습니다.

- **후보 = 유사도 상위 K ∪ 이름 언급:** 공급망처럼 사업 유사도가 낮은 관계를 찾는 데 합리적입니다.
- **공급·고객을 `supplies(공급자 → 고객)`로 통합:** 같은 사실을 중복 저장하지 않아 좋습니다.
- **다중 관계 허용:** 경쟁과 공급, 경쟁과 협력이 공존하는 사례를 표현할 수 있습니다.
- **배치 판정 + 읽기 중심 웹앱 + 별도 검수 저장소:** 현재 규모와 로컬 사용 목적에 적합합니다.
- **모델 어댑터와 캐시:** Jev의 실제 성능을 확인한 뒤 모델을 바꿀 수 있는 구조입니다.

1. **[높음] 쌍 단위 판정으로는 문장별 오탐 제거와 관계별 근거 연결을 구현할 수 없습니다.**

   [7.3절](/C:/Users/imyon/Documents/10-k-report/10-K-Report-Similarity/docs/relation-map-plan.md:314)의 `same_entity`는 근거 묶음 전체에 대해 답 하나를 반환합니다. 그런데 7.4절은 “기각인 언급 문장은 근거에서 뺀다”고 되어 있습니다. 현재 출력으로는 **어느 문장을 빼야 하는지 알 수 없습니다.**

   질문 자체도 두 문제가 있습니다. 항상 company B를 물으므로 B의 문서에 등장하는 A를 대칭적으로 처리하지 못하고, ‘과거 고용주인가’와 ‘동일 기업인가’를 섞습니다. 과거 고용주가 실제 그 기업인 경우에는 기업 식별은 맞고 관계 근거로는 부적절한 것입니다.

   - 언급별: 이 이름이 지정한 기업을 가리키는가?
   - 근거 구간별: 이 구간이 어떤 관계와 방향을 뒷받침하는가?
   - 기업쌍별: 유효한 근거들을 합치면 어떤 관계가 성립하는가?

   **원문 문장을 붙였다는 사실만으로 그 문장이 해당 관계의 근거가 되지는 않습니다.** `edge → evidence_id` 연결에도 검증이 필요합니다. Jev에도 문장 ID를 지정한 여러 질문을 한 요청에 넣을 수 있으므로, 문장별 판정이 반드시 문장별 요청을 뜻하지는 않습니다. 공식 문서도 state를 공유하면서 여러 질문을 병렬 평가하는 구조를 설명합니다. [TypeSafe 모델 문서](https://docs.typesafe.ai/models)

2. **[높음] 방향·시점·불확실성에 대한 출력 정의가 부족합니다.**

   지분은 `a_owns_b`, `b_owns_a`로 나누고, 공급도 양방향 질문을 대칭적인 문구로 작성해야 합니다. 특히 `relies on B`는 의존성을 나타낼 뿐 실제 공급 거래를 뜻하지 않을 수 있으므로 범위를 좁혀야 합니다.

   시간도 필요합니다. 계획 중인 제휴, 종료된 공급계약, 과거 지분 보유가 현재 관계와 섞일 수 있습니다. 최소한 `current / historical / planned / unclear` 같은 상태와 공시일·대상 기간을 구분하는 것을 권합니다.

   또 **사업 설명이 서로 맞아떨어진다는 이유만으로 실제 공급 관계가 있다고 추정하기는 어렵습니다.** 초기 버전에서는 `inferred supplies`를 별도 탐색 후보로 두거나 숨기고, 명시된 관계부터 검증하는 편이 좋습니다. `similar` 역시 “관계 없음”이 아니라 “검토 범위에서 직접 관계를 확인하지 못함”으로 설명해야 합니다.

3. **[높음] 정답셋과 평가 순서를 바꿔야 합니다.**

   [7.6절](/C:/Users/imyon/Documents/10-k-report/10-K-Report-Similarity/docs/relation-map-plan.md:402)의 독립 정답셋은 좋은 방향입니다. 그러나 같은 30개사로 질문·임계값을 고친 다음 모델 우열까지 평가하면 결과가 낙관적으로 나옵니다.

   **질문 개발용, 임계값 조정용, 최종 평가용 데이터를 구분**해야 합니다. 같은 쌍이나 근거 문서가 여러 세트에 중복되지 않게 하고, 기업 단위로 묶인 표본이라는 점도 평가에 반영해야 합니다.

   평가에는 다음 구분이 필요합니다.

   | 측정 대상 | 확인할 내용 |
   |---|---|
   | 후보 재현율 | 독립 정답 관계 중 후보 생성 단계가 찾은 비율 |
   | 근거 검색 재현율 | 관계를 입증하는 구간이 모델 입력에 포함된 비율 |
   | 판정 성능 | 적절한 근거가 주어졌을 때 유형·방향을 맞히는 정도 |
   | 전체 성능 | 후보 누락부터 최종 판정 오류까지 포함한 결과 |

   정답셋은 ‘실제로 알려진 관계’와 ‘대상 연도의 Item 1·1A에서 확인 가능한 관계’를 구분해야 합니다. 외부 지식으로만 알려진 관계를 현재 파이프라인의 추출 실패로 세면 해석이 어려워집니다.

   30개사·300개 관계는 **시범 평가에는 적절하지만, 유형별 정밀도 90%나 F1 차이 3%p를 확정하기에는 부족할 수 있습니다.** 예를 들어 한 유형에서 60건 중 54건을 맞혀도, 독립 표본을 가정한 Wilson 95% 구간은 약 80~95%입니다. 기업 간 의존성까지 고려하면 불확실성이 더 커질 수 있습니다.

   유형·확률 구간별 층화 표본은 전체 성능을 계산할 때 추출 확률에 따른 가중치도 필요합니다. 합격 기준에는 점추정치와 함께 유형별 표본 수·신뢰구간·자동 채택 비율을 넣는 것이 좋습니다.

4. **[높음] Jev가 부족할 때 ‘채택 후보만 LLM 재판정’하는 대안은 재현율 저하를 해결하지 못합니다.**

   - 채택·기각 임계값 근처인 경우
   - 명시적인 관계 표현이 있는데 판정 확률이 낮은 경우
   - 기업 식별이나 방향 판정이 충돌하는 경우

5. **[높음] 매출 비중을 같은 문장의 이름과 숫자로 연결하면 잘못된 수치를 저장하게 됩니다.**

SDK의 `system_one(model=...)`도 지원됩니다. 따라서 6,737쌍 × 3,000토큰의 **기본 판정 비용 약 $0.85** 계산은 맞습니다. 다만 문장별 추가 질문, 재판정, 재시도, 질문 개발 반복, LLM 출력 비용은 별도입니다. 약 6분은 요청 한도를 충분히 활용했을 때의 추정치로 표현하는 것이 정확합니다. [모델 사양](https://docs.typesafe.ai/models), [Python SDK](https://docs.typesafe.ai/sdk/python/api/clients/sync)

질문을 원자적으로 나누고 A/B 교환을 검증에 활용하자는 제안은 Jev의 공식 한계 설명과도 맞습니다. 공식 문서는 별도 질문 사이의 논리적 일관성을 보장하지 않으며, 불필요한 문맥이 정확도를 떨어뜨릴 수 있다고 설명합니다. [Jev 알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13) Cytoscape.js는 지정 좌표를 사용하는 `preset` 배치를 지원하므로 제안한 화면을 구현할 수 있습니다. [Cytoscape.js 배치 문서](https://js.cytoscape.org/#layouts/preset)

구현 순서는 다음처럼 조정하는 것을 권합니다.

1. **관계·근거·판정 상태·검수 키를 확정하고, 독립 정답셋 작성을 시작합니다.**
2. **0단계:** mentions·candidates와 최소한의 근거 확인 화면을 만듭니다. 후보 생성과 원문 추적을 검증합니다.
3. **1단계:** Jev·LLM 비교와 `eval-relations`를 함께 구현합니다. 질문과 임계값을 개발하고 별도 평가셋으로 확인합니다.
4. **2단계:** 평가를 통과한 설정으로 전체 판정 후 검수 화면과 관계도 표현을 완성합니다.
5. **3단계:** 외부 기업·주석·여러 연도·이벤트 분석으로 확장합니다.

가장 먼저 고칠 곳은 **7.3절의 판정 단위, 7.5절의 상태·검수 저장 구조, 7.6절의 평가 분리**입니다. 이 세 부분을 정리하면 기존 파이프라인을 활용하면서도 구현 중 큰 구조 변경을 줄일 수 있습니다.
